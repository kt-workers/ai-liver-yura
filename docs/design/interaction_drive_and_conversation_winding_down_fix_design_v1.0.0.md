# 画面操作区間反映と会話終了判定 修正設計 v1.0.0

## 1. 目的

実画面からの接触操作と通常会話を組み合わせた長時間動作ログで確認された、次の評価阻害要因を修正する。

1. 一つのドラッグ操作を構成する多数の座標サンプルが、それぞれ独立した内的状態刺激として加算される
2. 反対に、ドラッグ開始と終了だけを刺激として扱うと、長く撫でられている最中の反応が失われる
3. 「今日はそろそろ終わりにしようか」のような会話終了表現が、語尾だけを根拠に未対応Activityの実行要求へ分類される

## 2. 実動作で確認した事実

### 2.1 評価対象プロセス

対象プロセスは2026-08-02 03:00:10 JSTに起動し、09:59:39 JSTまで動作した。

Core発話確定境界の最終修正コミットは同日04:48:50 JSTに作成されているため、03:06から03:11頃に記録された自律発話の連続出力は、最終修正前から起動していた旧プロセスの結果である。この部分だけは最新HEADの自律発話間隔・話題終了判定の検証結果として扱わない。

一方、画面操作のサンプル単位状態更新と会話終了文の決定論的分類は、ログ取得後に最新HEADのコードへ照合しても残っていたため、本修正の対象とした。

### 2.2 画面操作

対象ログには236件の`USER_INTERACTION`が含まれていた。

- drag: 216件
- tap: 11件
- double_tap: 9件
- gesture_id: 19種類
- dragサンプル間隔: 平均約0.14秒
- 最長drag: 約11.3秒、79サンプル

生のdrag座標は約7回/秒で到着していた。全サンプルを意味上の新しい接触として扱うと、Drive・感情・欲求・道徳状態・関係性・履歴がブラウザのサンプリング頻度に依存して更新される。

発話については通常の接触クールダウンが12秒であり、最長11.3秒のdragでも開始後の途中反応が発生しない。開始と終了だけへ状態更新を限定する案でも、撫でられている継続時間が表現されない。

したがって、生の入力サンプル、内的状態へ反映する意味区間、声に出す反応区間を分離する。

## 3. 連続接触の三層契約

### 3.1 生入力層

Web画面は従来どおり`start / update / end`を送信する。座標追跡、接触位置、累積時間、境界判断に必要な情報を失わないため、生の送信頻度は変更しない。

### 3.2 内的状態反映層

`gesture_id`ごとに1.0秒の意味区間を作る。

| 入力 | 反映 | stimulus weight | 意味 |
|---|---|---:|---|
| start | 常に反映 | 0.35 | 接触開始への即時注意 |
| update・前回反映から1秒未満 | 反映しない | 0.00 | 同一区間内の座標追跡 |
| update・前回反映から1秒以上 | 反映 | 0.35 | 撫で続けられている次の区間 |
| end | 常に反映 | 0.15 | 接触終了 |

区間内で反映しないupdateは、次を変更しない。

- Drive
- Desire
- Emotion
- Moral State
- Relationship
- Episodic Memory
- Emotion History

これにより、長いdragでは1秒ごとに継続刺激が反映される一方、約0.14秒ごとの座標サンプルでは状態が飽和しない。

phaseと`continuous_contact`を持たない旧形式のdragは、一回の完結した単発操作として従来どおり扱う。既存Simulatorや旧クライアントとの互換性を維持する。

Driveの単位変化は既存量へ区間weightを掛ける。

```text
curiosity += 0.03 * weight
engagement += 0.08 * weight
boredom -= 0.08 * weight
energy -= 0.01 * weight
```

Traceには次を記録する。

- `interaction_segment_applied`
- `interaction_segment_index`
- `interaction_segment_reason`
- `gesture_id`
- `stimulus_scale`

### 3.3 発話反応層

声に出す反応は内的状態の1秒区間より粗くする。

- tapなど単発接触: 従来どおり12秒クールダウン
- dragなど連続接触: 4秒ごとに発話可否を再評価
- 境界要求・境界無視: 専用の既存クールダウンを優先

典型的な挙動は次になる。

```text
0秒   start: 即時反応候補
1秒   内的状態の継続更新
2秒   内的状態の継続更新
3秒   内的状態の継続更新
4秒   内的状態更新 + 発話反応候補
8秒   内的状態更新 + 発話反応候補
終了  弱い終了刺激
```

発話候補になっても、Response Policy、境界状態、実行中発話、Activity制約による最終抑制は維持する。

## 4. 会話終了判定契約

一般的な実行要求の語尾判定より先に、会話終了・別れの定型表現を判定する。

対象例:

- 今日はそろそろ終わりにしようか
- 今日はここまでにしよう
- また明日
- ばいばい
- おやすみ

これらは`UserRequestKind.CHAT`、reason=`conversation_winding_down`とする。

一方、対象Activityを明示した「エコー活動を終わりにしよう」などは、従来どおり実行要求として扱う。会話終了表現の追加によってPlugin Activityの開始・停止要求を奪わない。

## 5. 受入条件

1. 単発tapと旧形式dragの既存状態変化を維持する
2. 連続drag開始時に即時の状態反映がある
3. 同一区間内の高頻度updateでは状態と履歴が増えない
4. 1秒を超えて継続したdragでは、離す前にも状態が再度変化する
5. 4秒を超えて継続したdragでは、離す前にも発話反応の機会がある
6. 座標サンプル数だけを理由にEnergyやArousalが短時間で上下限へ張り付かない
7. 境界要求と境界無視の判定・専用発話制御を維持する
8. 「今日はそろそろ終わりにしようか」が通常会話へ流れる
9. Activityを明示した停止要求は実行要求のまま維持される

## 6. 主な回帰テスト

- 0.2秒後のdrag updateは同一区間として抑制される
- 1.05秒後のdrag updateは次区間として反映される
- 区間内updateでDrive・Emotion・Emotion Historyが変化しない
- 4秒未満の連続接触では再発話せず、4秒超で再発話候補になる
- 単発tapとphaseなしdragの既存挙動を維持する
- 会話終了文が未対応Activity実行要求にならない
- Activityを明示した停止要求は実行要求として残る

## 7. 再評価条件

最新HEADで実プロセスを新しく起動し、次を確認する。

1. 5〜10秒間、同じgesture_idでdragを継続する
2. Traceで区間内updateが`interaction_segment_applied=false`になることを確認する
3. 約1秒ごとに`interaction_segment_applied=true`とsegment indexの増加を確認する
4. 離す前に内的状態が段階的に変化することを確認する
5. 4秒以上継続したとき、途中で発話反応候補が生成されることを確認する
6. Energy・Arousal・Emotion Historyが座標サンプル数に比例して増減しないことを確認する
7. 「今日はそろそろ終わりにしようか」が通常会話になることを確認する
8. その後入力せず放置し、自律発話間隔と話題終了判定を確認する

修正前から起動し続けているプロセスは新しいコードを読み込まないため、必ず最新HEADで再起動したプロセスを評価する。
