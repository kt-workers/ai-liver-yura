# V2 作業ブランチ系統の整合性規約

Owner: #533
対象: ChatGPT手動運用 / Codex併用運用
Status: 実装・運用規約

## 1. 目的

同一Issueの作業を複数のブランチで重複実装したり、古いブランチの成果を本流へ取り込まないまま次工程へ進んだりすることを防ぐ。

この規約では、単に「現在の本流に似たコードが存在する」ことを作業完了の根拠にしない。

必ず、そのIssueで作られた各作業ブランチの成果がどのPR・commitで本流へ入ったか、またはなぜ入れないのかを説明可能な状態へ収束させる。

## 2. 用語

Issueに関係する各ブランチ・PRのまとまりを「作業系統」と呼ぶ。

各作業系統は次のいずれかへ分類する。

- `ACTIVE`: 現在採用して作業を継続している。
- `MERGED`: 本流へ取り込み済み。
- `SUPERSEDED`: 明示した後継作業系統へ置換済み。
- `ABANDONED`: 誤実装・不要化等の理由を記録して採用終了。
- `HISTORICAL`: 設計・検証等の履歴保存のみで、本流へ取り込まないことが明示済み。
- `ZERO_UNIQUE`: 現在の本流に対して固有commitを持たず、成果がすでに本流へ収束している。

分類できない作業系統は未解決とする。

## 3. 作業開始前の確認

Issueの実装を開始・再開する前に、GitHubの現在状態から次を確認する。

1. Issue番号に関連するopen / closed / merged PRを列挙する。
2. Issue番号・既知のbranch名から関連ブランチを列挙する。
3. 各ブランチを現在の本流と比較し、固有commitの有無を確認する。
4. 各作業系統をSection 2の状態へ分類する。
5. 現在採用する正規作業系統を1本に決める。

`ACTIVE`または未分類で、現在の本流に対して固有commitを持つ作業系統が存在する場合、新しい実装ブランチを作成してはならない。

古い作業系統が本流から大きく遅れていても、それだけを理由に新しいブランチで同じ機能を再実装しない。

## 4. 本流に似た成果物がある場合

本流に同じ、または似た成果物が見つかっても、既存作業系統を自動的に不要と判断しない。

次を確認する。

- その成果物を本流へ入れたPR / merge commitを特定できるか。
- 既存作業系統の変更項目が、その取り込みにより全件回収されているか。
- 設計書、試験、型契約、境界条件等の一部だけが欠落していないか。

由来を説明できない場合、作業系統は未解決のままとする。

## 5. 作業系統を置換する場合

新しい作業系統へ置き換える必要がある場合、旧系統を放置しない。

必須記録:

- 旧PRへ `SUPERSEDED_BY: #<後継PR>` を記録する。
- 後継PRへ `SUPERSEDES: #<旧PR>` を記録する。
- 旧系統の変更を「後継へ引継ぎ」「不要化」「誤実装」のいずれかへ分類する。
- 「本流に似たコードがあるため不要」だけを理由にしない。

誤実装をやり直す場合も、旧系統を`ABANDONED`または`SUPERSEDED`として理由付きで閉じる。

## 6. 古いブランチを現在の本流へ合わせる場合

既存の正規作業系統を継続できる場合、原則としてそのブランチを生かす。

- rebaseやforce pushで履歴を作り替えない。
- 必要なら現在の本流を既存作業ブランチへ通常mergeして整合させる。
- conflictがある場合は、元の作業成果と現在正本の双方を比較して同じ作業ブランチ上で解消する。
- 同じIssue用の別ブランチを新規作成してゼロから書き直すことを第一選択にしない。

## 7. 次工程へ進む前の確認

製造順で次のIssueへ進む前に、現在Issueについて次を確認する。

- 正規PRが本流へ取り込まれた、または明示的に採用終了している。
- 同一Issueに`ACTIVE`または未分類の作業系統が残っていない。
- 現在本流に対して固有commitを持つ未マージブランチがある場合、`SUPERSEDED / ABANDONED / HISTORICAL`の根拠がGitHub上に記録されている。
- 本流へ取り込む予定の成果物について、設計書・コード・試験の欠落がない。

これを満たさない限り次工程を開始しない。

## 8. Issue完了前の確認

Issueを`completed`へ変更する直前に、同一Issueの全PR・ブランチを再確認する。

完了禁止条件:

- 未分類の作業系統がある。
- `ACTIVE`な別系統がある。
- 現在本流に対して固有commitを持つ未マージbranchに処理理由がない。
- 取り込み済みと判断した成果について、どのPR/commitから本流へ入ったか説明できない。

通常mergeした場合は、必要に応じてレビュー済みHEADとmerge後treeの一致も確認する。

## 9. ChatGPT / Codexへの適用

ChatGPTが作業する場合も、Codexへ指示を渡す場合も同じ規約を適用する。

Codexへの実装指示には最低限、次を含める。

- 新規branch作成前に同一Issueの既存PR・branchを確認する。
- 未解決の固有commitを持つ作業系統がある場合は新規branchを作らない。
- 既存系統を継続するか、置換理由を明示してから進む。
- 「本流に同等実装がある」という理由だけで古いbranchを無視しない。
