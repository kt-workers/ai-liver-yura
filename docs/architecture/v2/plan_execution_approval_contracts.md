# 確定計画の承認範囲と活動進行の接続契約

所有Issue: #334（結合）、#361（計画）、#329（活動・実行事実）、#328（意識的な判断）。
設計起点: `9ec6893475328578e2b3a0513bcf67c3d8c33f75`。
状態: #334で具体化する公開契約。ユーザーが選択した「計画全体への明示的承認範囲で進行」を適用する。本流採用前であり、実装・検証の完了は別途確認する。

## 1. 権限と所有者

#328が確定計画全体への実行承認を明示する。#361による計画確定自体を実行承認へ昇格させない。承認済み範囲内の手順進行は決定論的な本番所有者が行い、手順ごとのLLM呼出し・再承認を一律には要求しない。#334は公開接続と処理の所有・回収を担い、判断の正本を新設しない。

承認の根拠は確定済みの実行判断と対象計画であり、任意文字列の`AuthorityRef`を組み立てただけでは許可にならない。外部提供先・検証基盤からの承認生成、計画確定印の偽造、非公開の検査回避は禁止する。

## 2. 承認に固定する範囲

新たな型付き承認には少なくとも次を束縛する。具体的な型と公開所有者の追加は関連設計と同時に実装・検証する。

- 判断識別子、意図参照、承認識別子、対象の確定計画識別子と内容。
- 対象目標とその版、文脈・注意・方針の必要な版。
- 許可された手順、能力要件、操作、対象、事前条件、完了条件。
- 手順の引数を取得する型付きの正規参照とその内容・版。現在の`ActivityPlanStep`に任意引数は存在しないため、接続処理が自由文や空の辞書から推測して作らない。
- 取消・割込み条件、期限、手順ごとの既存の再試行上限と失敗方針。

確定計画や目標の差替え、操作・対象・引数・能力範囲の拡張は既存承認の外側であり、新しい判断と承認を必要とする。単なる時刻の進行や無関係な版の変化で全計画を一律取消しにしない。各契約が依存すると宣言した版を検査する。

## 3. 手順選択と命令発行

依存手順の実行事実と完了条件の所有者が返す型付き判定を使い、開始可能な手順を選ぶ。手順が終端になっただけで完了条件を満たしたと推定しない。並行して実行可能な手順は、既存の資源上限・割込み・能力競合制約内で進行できる。遅い活動で無関係な認知・発話・身体処理を止めない。

発行直前に承認・計画・目標の有効性、必要な現在版、能力の現在利用可否、事前条件、期限、既存実行との重複を検査する。命令の`decision_id`と`authority`は承認へ由来を遡れるものとし、操作・引数は承認範囲と一致させる。

`SystemCommand`／`ActivityInvocation`を#329の公開入口へ渡す。再開対象の`resume_activity_id`は既存実行の照合を必要とし、新規実行への付替えや二重の外部作用を起こさない。#329の既存事前確認と実行事実の所有権を省略しない。

## 4. 結果・再試行・再計画

#329の確定結果・効果参照・未確認効果をそのまま評価・注意・次の判断へ戻す。現在文脈が変化しても、既に起きた外部作用の事実は消さない。計画進行の観測を別の実行事実正本にしない。

再試行は、承認済みの計画失敗方針と手順上限の内側だけで許可する。実行単位を新たに識別し、以前の結果と試行回数を保持する。効果が不明・適用された可能性がある場合、同じ操作を成功まで無条件に繰り返さない。既存の効果未確定性契約に従って、必要な照合を別の明示的活動とする。

上限到達、範囲外の変更、能力喪失、無効化された計画、再計画を要する失敗は、根拠付きの要求として評価・実行判断へ戻す。#361は承認された目標の計画を作るが、自分で別目標を選ばない。活動や計画の完了は#366の目標完了を自動確定しない。

## 5. 本体完成の検証

模擬能力提供先を使い、少なくとも次を本番の公開所有者を通して確認する。

- 能力0件の型付き利用不可、能力ありの汎用要求、失敗と結果の次の判断への返却。
- 承認なし・別計画・範囲外の操作／対象／引数の拒否。
- 依存付き複数手順、独立手順の並行性、重複投入・再開時の二重作用防止。
- 目標・文脈・能力の必要な版の変更と、確定直前の再検査。
- 承認範囲内の上限付き再試行、効果未確定時の安全な照合、再計画要求の返却。
- 取消・停止・再取消時の所有タスク回収と、確定済み実行事実の保持。
- 遅い能力実行中の入力・認知・発話・身体・背景処理の継続。

配信・ゲーム・具体プラグインの実接続を、この汎用境界の成立条件にしない。検証基盤は型付き入力と模擬提供先を供給するだけで、承認・手順選択・命令発行の判断を補作しない。


## 6. 公開型と承認の検査

実装時に次の公開型を追加する。通常の単純活動は既存の`ActivityIntentPayload`を使い、計画全体への承認と混同しない。

- `PlanExecutionScope`: #361の確定`ActivityPlan`、手順ごとの操作引数・事前条件の束縛、対象目標と各依存版、期限、方針世代を固定した承認対象。計画そのものの変更権限を持たない。
- `PlanStepExecutionBinding`: `step_id`、`operation_ref`、対象参照、固定した引数、引数の由来参照、解決済み事前条件。手順の操作・対象・事前条件参照と一致を検査する。引数の値を自由文から作る責務を結合処理へ置かない。
- `PlanExecutionIntentPayload`: 実行判断が選択する承認対象の参照。`ExecutiveIntentKind`に計画実行承認を追加し、対応する計画事実を`ExecutiveFactKind`で区別する。既存の活動意図から暗黙に昇格しない。
- `PlanExecutionAuthorization`: #328の確定判断と承認対象を照合して発行する承認。承認対象の内容・判断・意図の対応、必要な現在版、現在の能力・事前条件を発行時に再検査する。期限と再試行範囲を広げない。
- `PlanExecutionProgress`: 計画識別子、承認識別子、手順と実行識別子・試行回数・確定記録への参照、終了・再判断要求の根拠。#329の実行事実を所有し直さない。

承認対象は本番の公開所有者が登録・投影し、#328へ意味のある計画内容として渡す。参照文字列の一致だけで、登録されていない承認対象や改変された内容を許可しない。LLMが返す承認候補は、通常の確定判断の型・根拠・版・能力の検査を通る。未確定の判断候補や自作した承認オブジェクトでは活動を開始しない。

## 7. 容量・重複・終了の責務

計画の手順・依存・能力・参照の件数は既存D10の計画上限を維持する。新しい承認・進行記録・同時手順の保持には、明示的な上限付き方針を与える。上限到達時に古い実行事実を黙って捨てたり、新たな無制限タスクを作ったりしない。完了記録の明示回収と活動正本の保持は分ける。

開始予約は同期した状態遷移で高々1回とし、外部待機を予約の排他区間に入れない。能力呼出しと状態再取得の待機後に、結果・版・取消状態を正規所有者で再検査する。停止時は新しい手順を開始せず、既存の割込み可否に従って処理を回収し、実際の終端結果を保持する。

運転中の承認・実行途中の手順を、永続化層が無条件で再起動復元しない。既存#359の所有者による復元許可に従い、目標復元と実行再開を分ける。未確認の外部作用を再実行して解消したことにしない。

## 8. 判断から承認を発行する実装境界

`ExecutiveContextSnapshot`と`ExecutiveCommitState`に、承認対象となる確定計画の範囲を追加する。判断に提示する内容と確定時の内容を比較し、対象が変更・消失していれば承認しない。提示する計画の件数・手順・参照は明示した容量方針の上限内とし、超過を無制限保持や暗黙切捨てで処理しない。

`ExecutiveDecisionAuthority.commit`が通常の根拠・版・能力・事前条件の検査に加えて対象範囲を検査し、確定判断に対応する`PlanExecutionAuthorization`を同時生成する。確定判断の結果から承認を取得できるようにする。承認の生成が失敗した場合は、当該判断の確定済み記録も進めない。

承認は対象範囲全体、判断識別子、意図識別子、確定日時と有効期限を保持し、所有者の発行経路を通らない直接構築を拒否する。計画進行側は承認の実体を受け取り、任意の承認識別子から権限を復元しない。

計画承認意図は通常の活動命令へ直接投影しない。計画進行側が許可された各手順に対して命令を構成する際に、判断識別子と承認参照を維持する。発行する命令の操作・引数・能力・事前条件が対象手順の束縛と一致することを検査する。

同じ事前条件参照を複数手順で使う場合、述語・対象・期待値の相違を拒否する。確定判断に含める計画承認は、計画承認意図の集合と過不足なく対応し、対象範囲・確定時刻・容量方針の由来も一致させる。

判断に提示する計画承認対象は、既存の判断事実と合算して`max_fact_refs`以内とする。各対象の計画・引数・条件を含むJSON全体を`max_fact_payload_json_bytes`以内に制限し、既存の事実と同じ参照識別子を使わない。実行容量方針の各上限も対象の直列化内容に含める。

## 9. 応答完了時刻と承認確定時刻

LLMの応答完了時刻は候補が生成された時刻であり、承認の確定時刻ではない。`ExecutiveDeliberator`は`current_for_commit()`の待機が終わった後に、構成側から与えられた信頼できる時計を読み、その現在時刻を`commit_result()`と実行判断所有者へ渡す。既定の本番時計はUTCの現在時刻を返す。LLMの出力や検証対象の応答時刻を時計の代替にしない。

`commit_result()`には確定時刻を明示的に渡す。候補の生成時刻は引き続き応答完了時刻とするが、承認の有効期限と確定判断の時刻には現在状態取得後の時刻を用いる。状態取得中に期限を過ぎた場合は承認を発行せず、判断の確定済み記録も進めない。応答完了より前へ戻った確定時刻も拒否する。
